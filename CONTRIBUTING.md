# Участие в разработке

## Подготовка

Следуйте [инструкции по локальному запуску](docs/development/getting-started.md). Перед изменениями
прочитайте [описание архитектуры](docs/product/architecture.md) и правила для этого репозитория в
[AGENTS.md](AGENTS.md).

## Границы изменений

- Не используйте `organization_id`, `access_roles` или `role` из тела запроса как основание для выдачи прав.
- Каждый запрос к данным организации ограничивайте по организации и ACL до объединения результатов, повторного ранжирования и передачи контекста модели.
- Изменения ORM или схемы сопровождайте новой миграцией Alembic; существующие файлы миграций не меняйте.
- Изменения API, схемы или конфигурации синхронизируйте с документацией.
- Не добавляйте в Git секреты, `.env`, дампы баз данных и документы пользователей.

## Проверки

```bash
make lint
make test-smoke
make test
make typecheck
make test-frontend
```

Выберите проверки соразмерно изменению и укажите в запросе на слияние только те команды, которые действительно запускались.
Изменения поиска, разбиения текста на фрагменты, векторных представлений, полнотекстового поиска, повторного ранжирования
или запроса к модели требуют процедуры из [документа об оценке](docs/product/evaluation.md). Полная оценка не входит в
обычный CI и требует настроенной инфраструктуры и ключа для языковой модели.

## Запрос на слияние изменений

- Включайте в коммит одно логически связное изменение.
- Объясняйте причину и влияние изменения, а не только перечисляйте файлы.
- Указывайте влияние на миграции, конфигурацию, безопасность и откат.
- Не утверждайте, что проверка прошла успешно, если она не запускалась.
- Для документации проверяйте относительные ссылки, пути, команды и утверждения по коду.
