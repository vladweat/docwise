# Нефункциональные требования

Пороговые значения производительности — ориентиры для локального Compose и одной организации, а не соглашение об уровне обслуживания (SLA).
Нулевые утечки между организациями — обязательное требование. Реальные защитные границы описаны в
[обзоре безопасности](../security/overview.md) и [модели изоляции организаций](../platform/tenancy.md).

## Безопасность

| Область | Требование |
| --- | --- |
| Аутентификация | API использует HttpOnly-cookie только для текущего узла; проверяет активную сессию и членство в БД |
| Организация | `organization_id` берётся из сессии или БД, а не из тела запроса |
| ACL документов | `access_roles` применяется к списку, состоянию и оригиналу документа, а также к обеим веткам поиска до вызова модели |
| Кэш | Ключ учитывает организацию, поколение индекса и разрешённые роли |
| Аудит | Хранить поисковый запрос и ID фрагментов; не хранить полный текст фрагментов |
| Ошибки | Не возвращать трассировку стека, значения формы или сведения о чужом документе |
| Cookie | Для межсайтового режима требовать доверенный источник запроса и CSRF-заголовок; в рабочей среде использовать защищённую cookie |
| Секреты | Не добавлять в Git `.env`, ключи API, реквизиты доступа к хранилищу и реальные документы |

RLS на таблицах документов и фрагментов — дополнительный слой только при роли среды выполнения, не являющейся суперпользователем,
`docwise_rls`. Она не заменяет SQL-фильтры приложения.

## Надёжность обработки документов

- Обработчик загрузки сохраняет файл и ставит задачу Celery; разбор выполняется в фоновом обработчике.
- Повторные попытки ограничены временными ошибками; ошибки формата, разбора и квоты должны завершать задачу состоянием `failed`.
- Запись фрагментов и этапов обработки не входит в одну транзакцию с S3; повторную обработку и восстановление очереди проверяют отдельно.
- Удаление объекта S3 повторяется через транзакционную очередь `storage_deletions`.
- После потери Redis может потребоваться вручную просмотреть список задач и подтвердить их повторную постановку.

## Производительность и ёмкость

| Операция | Ориентир |
| --- | --- |
| Подтверждение загрузки | До 2 секунд, без разбора файла внутри HTTP-запроса |
| PDF около 20 страниц | Несколько минут; прогресс виден по состоянию документа |
| Время до первого ответа чата | Цитаты должны прийти до потока токенов; ранний `meta` может прийти раньше цитат |
| Поиск | Векторный и полнотекстовый поиск, RRF и повторное ранжирование без загрузки всего набора документов в память |

Запрещено выполнять `scroll` по всему набору документов ради одного запроса чата.

## Масштабирование

Публичный профиль использует один VPS, один экземпляр PostgreSQL, один Redis, один узел Garage и один планировщик Beat.
Перед масштабированием нужно определить RPO/RTO, при необходимости разделить критичные нагрузки Redis,
проверить пул подключений к БД и перенести секреты и средства наблюдения в сервисы, рассчитанные на рабочую среду.

## Наблюдаемость и качество

- `/health` проверяет процесс; `/ready` — зависимости и состояние оплаты.
- Структурированные журналы очищают чувствительные поля; Sentry подключается по желанию.
- Серверная часть предоставляет закрытые HTTP-метрики в формате Prometheus: число запросов и задержка. Централизованный сбор, панель мониторинга и распределённая трассировка не настроены.
- Качество поиска с генерацией ответа (RAG) отслеживается на контрольном наборе и примерах с запрещённым доступом; текущие результаты приведены в [оценке](evaluation.md).

## Совместимость

Идентификаторы API и переменных конфигурации остаются на английском. Пользовательский интерфейс и документация могут быть переведены;
сообщения об ошибках API должны оставаться безопасными и пригодными для перевода.
